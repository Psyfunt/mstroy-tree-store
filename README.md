# mstroy-tree-store

Тестовое задание MStroy (Frontend, Vue.js): класс `TreeStore` и таблица-дерево на AG Grid по макету из ТЗ.

## Запуск

Нужен Node.js 22.18+ или 24.12+.

```sh
npm ci
npm run dev
```

Страница откроется на http://localhost:5173. Первые 2 секунды таблица показывает «Загрузка…»: задержку загрузки требует ТЗ. Потом появляются строки из `public/items.json`.

| Команда              | Что делает                        |
| -------------------- | --------------------------------- |
| `npm test`           | все тесты один раз                |
| `npm run test:unit`  | тесты в режиме наблюдения         |
| `npm run coverage`   | тесты с отчётом о покрытии        |
| `npm run bench`      | бенчмарки TreeStore               |
| `npm run type-check` | проверка типов (vue-tsc)          |
| `npm run lint`       | oxlint и ESLint                   |
| `npm run build`      | проверка типов и сборка в `dist/` |

## TreeStore

Класс лежит в `src/tree-store/TreeStore.ts` и ни от чего не зависит: ни от Vue, ни от сборщика. В файле только тот синтаксис TypeScript, который просто стирается, поэтому его можно подключить в любой раннер тестов. Импорт — как удобнее:

```ts
import { TreeStore } from './src/tree-store/TreeStore'
import TreeStore from './src/tree-store/TreeStore'
```

Рядом экспортируются типы `TreeItem` (`id` и `parent`) и `TreeItemId` (`string | number`).

Внутри два индекса: элементы по id и дети по id родителя (тоже `Map`, с сохранением порядка). Оба строятся за один проход, поэтому методы не перебирают весь массив, а трогают только то, что возвращают или меняют: удаление и замена не ищут элемент среди соседей, сколько бы их ни было.

| Метод                | Что делает                                                                           | Сложность                           |
| -------------------- | ------------------------------------------------------------------------------------ | ----------------------------------- |
| `getAll()`           | все элементы в порядке добавления                                                    | O(1), после изменения O(n) один раз |
| `getItem(id)`        | элемент или `undefined`                                                              | O(1)                                |
| `getChildren(id)`    | прямые дети                                                                          | O(число детей)                      |
| `getAllChildren(id)` | все потомки по уровням: сначала дети, потом их дети и так далее                      | O(размер поддерева)                 |
| `getAllParents(id)`  | `[сам элемент, родитель, …, корень]`                                                 | O(глубина)                          |
| `setItems(items)`    | заменяет всё содержимое                                                              | O(n)                                |
| `addItem(item)`      | добавляет в конец; родитель может появиться и позже                                  | O(1)                                |
| `removeItem(id)`     | удаляет элемент вместе с поддеревом                                                  | O(размер поддерева)                 |
| `updateItem(item)`   | заменяет элемент с тем же id; если сменился родитель, элемент уходит в конец списков | O(1)                                |

Что ещё стоит знать о поведении:

- Для неизвестного id `getItem` вернёт `undefined`, остальные методы чтения — `[]`, а `removeItem` и `updateItem` ничего не сделают.
- id сравниваются строго: `1` и `'1'` — разные элементы.
- Массив, который стор уже вернул, он потом не меняет. `getAll()` до следующего изменения отдаёт один и тот же массив, поэтому он типизирован как `readonly`.

### Типы

Тип элементов выводится из массива в конструкторе, его можно указать и явно:

```ts
const store = new TreeStore(items) // тип берётся из items
const empty = new TreeStore<Item>([]) // пустой старт с типом
```

Пустому стору без указанного типа можно отдавать элементы с любыми полями, обязательны только `id` и `parent`. А вот читать свои поля, например `store.getItem(1)?.label`, TypeScript разрешит, только если тип указан явно. Ещё одно: если тип выведен из массива, то элемент с другим сочетанием типов `id` и `parent` (скажем, строковый id у корня, когда в массиве таких не было) добавится только при явном типе. Так же ведут себя `Set` и `Map`.

### Быстродействие

`npm run bench`, 100 тысяч элементов, среднее время одного вызова (Node 24, ноутбук разработчика):

|                                | случайное дерево | широкое дерево |
| ------------------------------ | ---------------- | -------------- |
| конструктор                    | 85 мс            | 36 мс          |
| `getAll`, `getItem`            | ~0,1 мкс         | ~0,1 мкс       |
| `getChildren`                  | 0,4 мкс          | 0,1 мкс        |
| `getAllChildren` (от корня)    | 30 мс            | 3,0 мс         |
| `getAllParents`                | 2,1 мкс          | 0,4 мкс        |
| `addItem` + `removeItem`       | 1,9 мкс          | 1,3 мкс        |
| `updateItem` (тот же родитель) | 1,4 мкс          | 0,6 мкс        |

В случайном дереве каждый элемент висит на случайном из созданных раньше, а сам массив перемешан. В широком — один корень и 99 999 его детей. Время изменений не зависит от формы дерева: дети хранятся не массивом, а `Map`, и удаление или замена не ищут элемент среди соседей. На массивах то же `updateItem` в широком дереве занимало 20 мкс, а удалить или обновить все 100 тысяч детей одного родителя по одному стоило больше секунды. Цена `Map` — построение медленнее примерно в полтора раза и больше памяти на глубоких деревьях (цепочка в 100 тысяч уровней: 25 МБ против 12). Миллион элементов строится примерно за секунду.

Кроме бенчмарков есть тест-потолок `TreeStore.perf.spec.ts`: 100 тысяч элементов, все методы, не больше 2 секунд на сценарий, в том числе обновить и удалить по одному всех детей широкого дерева. Он входит в `npm test` и упадёт, если какой-то метод скатится к O(n²).

## Таблица

`src/components/TreeTable.vue` — AG Grid с Tree Data из Enterprise. Дерево строится по полю `parent` и на старте раскрыто целиком, как на макете. В «Категории» стоит «Группа», если у строки есть дети, иначе «Элемент». «№ п\п» — номер строки в том виде, в каком её видно: если свернуть группу, номера идут подряд без пропусков.

`App.vue` создаёт пустой стор, через 2 секунды загружает `items.json` через `fetch` и передаёт данные в `setItems`. Файл лежит в `public/`, поэтому в бандл не попадает.

Таблица читает `store.getAll()` через `computed`, а сам стор в приложении обёрнут в `shallowReactive`. Каждый метод записи сбрасывает кэш `getAll` присваиванием, Vue это замечает, и таблица перерисовывается после любого изменения стора без перезагрузки страницы. Сам класс при этом остаётся обычным TS-классом без Vue внутри.

## Тесты

102 теста на vitest:

- TreeStore: каждый метод на данных из ТЗ, изменения, типы;
- сверка с простой эталонной моделью: 50 случайных деревьев по 300 случайных операций, после каждой сравниваются ответы всех методов;
- потолок производительности;
- загрузка данных: `fetch` вызывается ровно через 2 секунды;
- таблица и приложение в jsdom: «Загрузка…» все 2 секунды, порядок и уровни строк как на макете, подписи колонок, свёртка группы с перенумерацией, обновление после `setItems`, `addItem`, `removeItem` и `updateItem` без пересоздания таблицы, дерево из данных, где дети идут раньше родителей; точка входа монтирует приложение и показывает дерево из `items.json`.

## Ограничения

- AG Grid Enterprise без ключа показывает водяной знак и пишет в консоль баннер о лицензии. Для ознакомления это нормально, ТЗ разрешает бесплатный пакет из npm.
- Стор рассчитывает, что id уникальны, циклов нет, а `updateItem` получает элемент целиком. Если это не так, поведение не определено: ТЗ таких проверок не требует, а каждая стоила бы времени на каждой операции.
- AG Grid требует строковый id строки, поэтому данные, где одновременно есть `1` и `'1'`, таблица покажет неправильно. В самом сторе это два разных элемента.
- Ошибки загрузки не обрабатываются, по ТЗ это не нужно: если `items.json` не придёт, таблица так и останется в состоянии загрузки.
- `npm audit` показывает уязвимости в `braces` — это транзитивная зависимость конфигурации ESLint, только для разработки, в сборку она не попадает. Без ломающих обновлений линтера не закрывается.
- Кнопок для изменения данных в интерфейсе нет, в ТЗ их тоже нет. Таблица получает данные через `setItems`, а то, что она обновляется после любого другого метода записи, проверяют тесты.
